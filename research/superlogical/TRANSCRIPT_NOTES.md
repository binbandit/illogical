# Timestamped narration notes

These are paraphrased research notes from the six narrated X previews, organized around features and architecture. All six had accessible English caption tracks. Local Whisper transcription supplemented two clips, especially a missing passage in the session-management captions. Automatic captions can mishear names such as Ghostty, Rex, PTY, and command names; visible UI and code take precedence for spelling.

The complete narration remains available at each original source link. Offsets below are approximate starting points within the video. These notes are not verbatim transcripts or a claim that machine recognition was manually verified word for word.

## V02: architecture, 10:40

[Original video](https://x.com/mitchellh/status/2082936029426892960) · 30 July 2026 UTC

| Offset | Explanation and consequence for illogical |
|---|---|
| 0:31 | Compares conventional multiplexers' emulation and rendering path with their proposed arrangement. Treat the comparison as the author's explanation, not a benchmark of every existing multiplexer. |
| 1:57 | On attachment, take a coherent binary snapshot of terminal state. Printed screen text alone is insufficient. |
| 2:25 | Dimensions, terminal modes, cursor, and related state are part of reconstruction. A short synchronization boundary is necessary. |
| 3:00 | The client becomes ready after receiving the active terminal state; full history is not on the initial interactive path. |
| 3:29 | Distribute PTY output to client emulators as well as the authoritative server emulator. Avoid reconstructing a client terminal exclusively from server screen differences. |
| 4:23 | Serialize input through the server. Multiple clients can observe the same terminal. |
| 5:00 | Load scrollback asynchronously, with newer portions first. Client scrolling and selection are independent. |
| 5:59 | A new snapshot can bring a divergent client back into agreement. |
| 7:10 | Tabs, windows, and splits are native layouts around individual terminal streams. |
| 7:52 | Full legacy-terminal layout compatibility remains undecided; single-stream attachment through a compatibility path is intended. |
| 9:34 | Terminal capabilities depend on what the server's terminal engine understands, not arbitrary opaque passthrough of every future protocol. |

Build implication: prove snapshot restoration and live continuation before building a large UI shell. The public Ghostty snapshot API now provides concrete implementation evidence for much of this model.

## V11: resource use and parking, 11:43

[Original video](https://x.com/mitchellh/status/2095232081853039041) · 2 September 2026 UTC

| Offset | Explanation and consequence for illogical |
|---|---|
| 0:11 | The server is described as fully self-hosted, starting automatically with the Mac app and also running separately on Linux. |
| 1:57 | Discusses potential scale as agents create large numbers of terminals. This is motivation, not a demonstrated load test. |
| 3:13 | Compares filled-terminal memory use. Measurement methodology was not independently checked. |
| 3:55 | Introduces parking as a way to make inactive terminals inexpensive. |
| 4:21 | After approximately 60 seconds without PTY output, persist emulator state and release its memory. |
| 5:03 | Input alone need not wake the emulator; output does. An attached idle terminal can still park. |
| 6:04 | Describes fast restoration from a compressed snapshot. Exact performance numbers depend on measurement boundaries. |
| 6:44 | Active PTYs use dedicated readers; idle ones can move to a shared event poller so per-terminal thread resources are released. |
| 9:06 | Client-side buffers can also be released while idle. |
| 11:00 | An attaching client can receive an already parked snapshot without necessarily waking the server emulator. |

Build implication: parking concerns the terminal representation and I/O machinery. It does not stop the user's shell or checkpoint a running application across reboot. Resource optimization should follow a correct attach/snapshot implementation.
